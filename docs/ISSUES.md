# 当前遇到的问题（2026-09-18 实测）

> 本文档记录**阻碍项目推进的障碍**，不是待办清单，也不是方案。
> 所有数字均由文末命令在本地实测得到，可复核。

## 摘要

三条互相锁死的链：

1. **源素材只有 4.53 分钟。** 而微调的官方下限是 1~10 小时，差 **13~130 倍**。
   更麻烦的是：现有管线的产出率**已经很高**（源素材的 70.4% 已成为候选语音、
   27.7% 成为交付），**没有可挤的水分**——瓶颈完全在素材量，不在方法。
2. **Ground truth 只有 2 条人工标注**，其余 43 条是弱标注。无法评估任何新管线。
3. **没有播放设备，TTS 无法做听感验证**，而 TTS 的本质是主观任务。

在这三条解决之前，换模型、换工具链、重建数据集都不会改变结果。

## 一、数据基线（实测）

| 层级                    | 数量                        | 时长                        |
| ----------------------- | --------------------------- | --------------------------- |
| 源素材                  | 9 个片段（21.4~45.9s）      | **271.9s / 4.53min**        |
| VAD 候选句              | 80                          | 191.5s（源的 **70.4%**）    |
| 已标注                  | 45（56.2%）                 | —                           |
| 判定为奶龙（`label=1`） | 22（候选的 27.5%）          | —                           |
| 最终交付                | 11 段（由 22 句合并，见下） | **75.3s**（源的 **27.7%**） |

候选句平均 2.39s，范围 0.92~11.0s。按源分布：

| 源     | 候选句 | 候选时长 |
| ------ | ------ | -------- |
| src_01 | 8      | 17.2s    |
| src_02 | 3      | 13.7s    |
| src_03 | 15     | 38.2s    |
| src_04 | 7      | 16.4s    |
| src_05 | 11     | 24.2s    |
| src_06 | 9      | 22.8s    |
| src_07 | 9      | 18.3s    |
| src_08 | 8      | 21.7s    |
| src_09 | 10     | 18.9s    |

> 交付段数（11）少于组 A 句数（22），不是过滤损失，是 `finalize` 按
> `GAP_TOL=0.80` 把相邻句合并成 3.0~10.0s 连续片段的结果。

**关键读数：产出率已经很高，几乎没有可挤的水分。**

- 源 → 候选 70.4%（说明 VAD 没有大量漏切）
- 源 → 交付 27.7%
- 候选 → 交付 39.3%

⇒ 重建管线最多能把交付率从 27.7% 提到接近 70.4%（放宽说话人判定），
即 **75.3s → 191.5s，2.5 倍**。而目标差距是 **48 倍**。
**优化管线救不了这个项目。**

## 二、核心问题：素材量差 13~130 倍

按现有产出率外推（源 271.9s → 交付 75.3s，即 27.7%）：平均每个源片段
（30.2s）产出 **8.37s 交付 / 1.22 段**。

| 目标                                 | 需要的源素材               |
| ------------------------------------ | -------------------------- |
| 150 条样本（CosyVoice 官方条数下限） | ~62 min（约 123 个片段）   |
| 1 小时交付（CosyVoice 官方时长下限） | **3.6 h（约 430 个片段）** |
| 10 小时交付（同口径上限）            | 36 h（约 4300 个片段）     |

（若只要"候选语音"1 小时、不做说话人判定，按 70.4% 产出率需 85 分钟源素材。）

两个官方口径**互相矛盾**：150 条按实测候选句均长 2.39s 算约 **6 分钟**，
按交付段均长 6.85s 算约 **17 分钟**；而时长口径要 **60 分钟**。
**差 3.5~10 倍，且不知道哪一条在约束我们。** 这条必须回去澄清
（注意该口径出自阿里云百炼对 `cosyvoice-v3-flash` 的 SFT 文档，
**是否适用于开源权重自训尚未确认**）。

⚠️ `~430 个片段` 是"源片段"不是"剧集"。按每集 1~3 分钟估算，
对应 **200~400 集**可下载内容。这是纯工程量问题，不是算法问题。

## 三、Ground truth 几乎为空

- 45 条标注中 `source=human` 仅 **2 条**（即 `config.HUMAN_SEED`），其余 43 条 `weak`
- 也就是说"22 条是奶龙"这个判定，建立在 2 条人工 + 43 条弱标注之上
- 而上一轮已验证这组锚点本身不成立（两两余弦 0.42~0.70，同人通常 >0.70）

⇒ **没有可信 ground truth，就无法评估任何新管线、新模型、新工具。**
这项必须先于"换什么模型"解决。

## 四、目标说话人提取是循环依赖

要提取奶龙的声音 → 需要奶龙的声纹参考 → 参考只能从混音里提取。三种绕法都有已确认缺陷：

1. **整片段平均嵌入**（上轮做法）—— 假设整片段以同一人为主，在本批素材上未验证
2. **纯音频分离** —— 官方自承输出两轨但**无法确定哪一轨是目标**
3. **AV-TSE（看脸识声）** —— 要求 ≥720p、人脸占画面 1/5~1/4、角度 ≤30°、
   "背影无效"、不支持纯音频输入、一次只提一人；**卡通角色的人脸检测可靠性未知**

⚠️ 本轮的搜索存在一个**已知缺口**：基于声纹注册的**纯音频** TSE
（WeSep / USEF-TSE / TF-GridNet / SpeakerBeam 类）**完全没有搜过**。
对卡通素材（人脸可能失效）这可能是唯一出路。**"没搜到"不等于"不存在"。**

## 五、没有耳朵，TTS 迭代循环是半盲的

环境无播放设备。可自动化的替代指标只有两个：

| 指标             | 测什么     | 可否自动化 | 已知问题                                   |
| ---------------- | ---------- | ---------- | ------------------------------------------ |
| ASR 反算 CER/WER | 内容读对没 | 是         | 卡通语音的 CER 完全未知（见第八节）        |
| 声纹模型算 SIM   | 音色像不像 | 部分       | 退化为"短句 vs 短句"，该路线上一轮已被证否 |

上一轮结论：2s 句两两余弦中位仅 0.445，无簇结构；可靠的是 30s 长参考（同源 0.81~0.92）。

⇒ 能判断"读对了没"，**不能可靠判断"像不像"**。选型和微调都缺反馈信号。

## 六、素材属性与训练需求本质冲突

| 想要的（资产）       | 训练要求的（约束）       |
| -------------------- | ------------------------ |
| 夸张表演、独特语气   | 干净、单说话人、韵律规范 |
| 笑/叹/拟声是角色特征 | (音频, 文本) 必须配对    |

同一个"夸张"既是资产又是污染源。非语音发声 **ASR 转不出文本** →
只能丢弃或错标，两者都损害模型。

## 七、选型的硬信息缺失

- **license 未确认**：MOSS-TTS、CosyVoice 2/3、IndexTTS 2、VoxCPM、GPT-SoVITS、
  ClearerVoice、SenseVoice/Paraformer
- **确认可商用**：仅 Qwen3-TTS（Apache-2.0）、dots.tts（Apache-2.0）、
  VibeVoice / Chatterbox（MIT）
- **明确排除**：F5-TTS（CC-BY-NC，权重非商用）
- 所有中文 CER/SIM 数字**均来自竞品自建对比表**，且互相矛盾
  （Qwen3-TTS 在两张表中指代不一致）
- **"支持微调"多为营销声明**：除 MOSS-TTS 家族有完整 finetune 文档
  （`prepare_data.py` / `dataset.py` / `sft.py` / `run_train.sh`，
  Nano 单卡训练峰值 3.23 GiB）外，**没有一个模型有可验证的微调成功记录**
- 唯一的实测反例：1200 条 LoRA 微调 IndexTTS → **过拟合、零样本克隆能力丢失**

## 八、卡通语音的 ASR 可靠性零数据

搜到的中文 CER（SenseVoice 7.81% / Fun-ASR-Nano 8.06% / Paraformer-zh 10.18% /
Whisper-large-v3 20.02%）**全部来自朗读、会议、通用长音频**，
**没有一个针对动画配音或音效密集素材**。而微调对 (音频, 文本) 错误极度敏感。

## 九、未决决策

以下四项未定，在确定前任何方案都只是猜测：

1. 数据来源（继续奶龙并扩大 / 换素材 / 先用公开数据集跑通）
2. GPU 与显存（决定哪些模型能微调）
3. LLM 与 ASR 在管线中的角色（运行时闭环 vs 仅构建期）
4. 是否商用（决定 license 筛选强度）

## 十、排序

必须先解决（否则后续全是白做）：

1. **素材量** — 决定项目可行与否（第二节）
2. **ground truth** — 决定能否评估（第三节）
3. **TSE 路径** — 决定数据能否取出（第四节，含信息缺口）
4. **评估手段** — 决定能否迭代（第五节）

可后置：license 核实、卡通 ASR 实测、模型选型。

## 十一、两种可能的重新框定

**A. 放弃微调，只做零样本克隆 + 精做参考音**

9 个片段的素材**是够的** —— 从现有 11 段里挑最干净的 3~4 段拼成 30s 参考音即可，
430 个片段的缺口直接消失。能否成立**完全取决于第五节**：能不能验证"像不像"。
若不能验证，这条路一样是盲的。

**B. 先解决素材量**

把源素材从 4.5 分钟扩到小时级，即下载/处理 200~400 集。
纯工程量问题，但需要先确认第九节第 2、4 项（算力与商用）。
